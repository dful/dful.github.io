AI/Fundamentos

Razonamiento

Reasoning effort cambia el trabajo que el modelo dedica a una request; conviene medirlo contra calidad, latencia y consumo en la tarea real.
Actualizado 6 oct 2026

Algunos modelos permiten ajustar cuánto trabajo dedican a una request antes de producir la respuesta o decidir la siguiente acción. Las APIs y los harnesses suelen exponerlo como reasoning effort, con niveles como low, medium o high.

Ese control no describe el proceso interno paso a paso. Sirve para dar más o menos margen a tareas donde hay que relacionar evidencia, probar hipótesis o corregir una decisión después de observar un resultado.

Cuándo subir el effort

Extraer un valor de un JSON o clasificar una entrada sencilla suele necesitar poco reasoning. Investigar por qué falla un test ambiguo puede requerir leer varios ficheros, relacionar un cambio reciente, ejecutar el test y revisar el error siguiente.

En tareas así, más effort puede mejorar la investigación, aunque también puede aumentar la exploración innecesaria. La forma práctica de escogerlo es probar varios niveles sobre trabajo representativo y comprobar en cuál empieza a estabilizarse el resultado.

Si medium resuelve de forma consistente el tipo de tarea que importa, high solo merece la pena cuando mejora algo medible: corrección, tasa de éxito o número de intervenciones necesarias.

Latencia, tokens y coste

Más reasoning suele aumentar la latencia y el consumo. La contabilización concreta depende de la API: un proveedor puede incluir ese trabajo dentro del output usage, detallarlo por separado o exponer métricas distintas.

Para comparar configuraciones conviene registrar al menos:

  • Si la tarea terminó correctamente.
  • Cuánto tardó.
  • Cuántos tokens o llamadas consumió.

En una request aislada la diferencia puede ser pequeña. En un agente, el coste se repite a lo largo de muchas inferencias y puede amplificarse con reintentos o subagentes. Costes de API desarrolla ese cálculo.

Reasoning dentro del agent loop

El reasoning de un agente ocurre entre observaciones, no únicamente antes de la respuesta final. Puede leer un fichero, observar el resultado, cambiar de hipótesis y ejecutar un test; el nuevo output condiciona la siguiente decisión.

Por ejemplo, un coding agent puede empezar sospechando de la implementación, leer el test y descubrir que la expectativa quedó desactualizada. Esa evidencia cambia el siguiente paso dentro del bucle de agente.

Un effort mayor puede cambiar tanto el análisis como las tool calls que el modelo decide realizar. Para evaluarlo interesa el comportamiento del run completo, no la longitud de la explicación visible.
