Estado de un agente

Qué registra la aplicación para que un agente pueda retomar una tarea y verificar los cambios en el sistema sobre el que trabaja.
Actualizado 11 oct 2026

La aplicación conserva el estado de trabajo del agente entre llamadas. Antes de cada decisión, prepara el contexto que recibirá el modelo; el modelo devuelve una respuesta o solicita una tool call. La API, el repositorio o el servicio mantienen su propio estado, que puede cambiar mientras dura la tarea.

Las flechas muestran el ciclo: el agente observa el entorno, la aplicación registra el resultado y prepara la información para la siguiente llamada. Una acción puede solicitar un cambio en el entorno; la siguiente observación permite actualizar el registro.

Un registro que se pueda usar

Supongamos que un agente comprueba si user_b puede modificar una factura de user_a en una API de prueba. Su registro de trabajo podría ser:

objective: verify-cross-account-write
scope:
  origin: https://api.example.test
  identities: [user_a, user_b]
  allowed_actions: [read, replay, reversible-write]
observations:
  - id: obs-014
    source: GET /api/invoices/1042 as user_a
    value: "owner=user_a; note=before"
    observed_at: 2026-10-05T09:12:00Z
    evidence: artifacts/requests/obs-014.http
hypotheses:
  - id: hyp-003
    claim: "user_b can change invoice 1042 despite owning a different account"
    based_on: [obs-014]
    status: unverified
actions:
  - id: act-021
    operation: PATCH /api/invoices/1042 as user_b
    marker: auth-check-01
    result: timeout-unknown
    observed_at: 2026-10-05T09:15:00Z
pending:
  - read invoice 1042 as user_a and compare its note with obs-014
checkpoint:
  step: verify-write-effect
  request_log: artifacts/requests/act-021.http

El registro separa las observaciones, las hipótesis y las acciones. El log conserva los bytes exactos de la request; obs-014 señala dónde encontrarlos sin copiar el intercambio entero al contexto. hyp-003 sigue pendiente hasta que una lectura posterior confirme qué ocurrió. Como el PATCH terminó en timeout, el resultado queda como unknown hasta comprobar la factura.

Guarda literalmente los paths, IDs externos y hashes que permitan recuperar el mismo recurso. El resumen explica por qué se probó la factura 1042, y las requests y respuestas conservan la evidencia. Para los tokens, guarda una referencia a un almacén de secretos controlado.

Qué entra en contexto

Para decidir el siguiente paso, el modelo necesita el objetivo, el alcance de la prueba, la propiedad conocida de la factura, el resultado incierto del PATCH y la verificación pendiente. El log HTTP completo puede quedar como artefacto; la aplicación recupera el intercambio exacto cuando hace falta.

La selección cambia con la tarea. Cuando el agente vuelve a leer la factura, la respuesta nueva pasa a ser la evidencia más reciente y el baseline queda disponible para comparar. Antes de otra request, la aplicación puede recuperar el alcance, las reglas de autorización y el intercambio HTTP pertinente.

Después de una tool call

El runtime registra la operación intentada, sus argumentos, el resultado y cuándo se observó. Para confirmar una escritura, lee el recurso otra vez y compara el valor guardado. Una respuesta de error requiere revisar el estado final: la operación pudo no empezar, ejecutarse parcialmente o terminar mientras se perdía la respuesta.

Un timeout después de una acción con efectos es ambiguo. Si el PATCH anterior agota el tiempo de espera, lee la factura como su propietario antes de repetir la escritura. Compara la marca y el valor original, y registra completed, not-applied o unknown. Si la API admite una clave de idempotencia o un ID de operación, consérvalo con la acción.

Datos que caducan

observed_at registra cuándo se vio un dato; su vigencia depende de los cambios posteriores. La propiedad de una factura, los permisos, el estado de un job o la respuesta de una API pueden cambiar mientras el agente trabaja. Revalida antes de una acción que dependa de ese dato, sobre todo después de una pausa o si otra persona pudo intervenir.

Al reanudar, recupera el paso y las referencias guardadas. Antes de continuar, comprueba la factura y el estado de la sesión: el sistema objetivo puede haber cambiado durante la pausa. Si la marca ya aparece en la factura o el token ha caducado, ajusta la siguiente request al estado observado.

Estado del agente entre llamadas

El estado del agente es el registro de trabajo que la aplicación conserva para continuar: objetivo y alcance, observaciones con referencias a evidencias, hipótesis, acciones y resultados, siguiente paso y checkpoint. Antes de cada llamada, la aplicación selecciona de ese registro la información que el modelo necesita para decidir; esa selección forma el contexto. El entorno mantiene su propio estado, que se consulta cuando la siguiente acción depende de su valor actual.
